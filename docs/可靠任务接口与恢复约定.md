# 可靠任务接口与恢复约定

更新：2026-10-09。V5 可靠任务及可信采集已随只读版本上线，生产业务控制仍关闭；此前独立真实 Docker 容器验收见[开发进度](开发进度.md)。本轮新增 V6 UNKNOWN 人工核对源码，尚未部署，契约见[UNKNOWN 任务人工核对设计](UNKNOWN任务人工核对设计.md)。任务使用中央持久队列、Agent Inbox、受控执行与结果查询；核对独立于原命令，不重放或改写原 UNKNOWN，AI 后置。

## 任务身份与状态

中央生成固定 UUID `commandId`，Agent 的 `taskId` 等于它。浏览器以 UUID `Idempotency-Key` 标识一次明确操作，网络重试保持同一键。相同键和相同实例、动作、预期执行模式返回原任务；改变内容返回 409。历史任务保留但标为 `LEGACY_MOCK`，永不自动下发。

中央状态为 `PENDING/DISPATCHING/DELIVERED/RUNNING/RETRY_WAIT/SUCCEEDED/FAILED/UNKNOWN`，Agent 状态为 `PENDING/RUNNING/SUCCEEDED/FAILED/UNKNOWN`。`UNKNOWN` 表示结果不确定，需要核对，不能当失败后自动重做。执行模式使用 `MOCK/DOCKER/LEGACY_MOCK/UNKNOWN`。任务成功不得改写实例观测状态。

## 浏览器与控制中心

| 接口 | 契约 |
|---|---|
| `GET /api/control/capabilities` | `{controlEnabled,canControl,allowedActions,targets:[{instanceId,executionMode,allowedActions,blockingTaskId,blockedReason,canConfirmPending}],reason}`；模式和互斥来自服务端，未知或不允许的目标不提供可执行动作 |
| `POST /api/instances/{centralId}/actions` | Bearer 操作令牌、`Idempotency-Key`；正文 `{action:"START|STOP|RESTART",expectedExecutionMode:"MOCK|DOCKER"}`；新建及幂等返回均为 HTTP 202、统一外壳中的 Task |
| `GET /api/tasks`、`GET /api/tasks/{id}` | 列表返回最近 100 条；详情返回任务及来源、目标身份、创建/更新时间、命令 ID、投递次数、固定结果码 |
| `GET /api/tasks/{id}/events` | 按 `sequence` 升序返回 `{id,taskId,sequence,fromStatus,toStatus,actor,reason,occurredAt}` |

Task 保留 `id/instanceId/action/status/message/createdAt/finishedAt`，新增 `nodeId/agentInstanceId/commandId/executionMode/requestedBy/updatedAt/attempts/resultCode`，其他调度字段可仅在后端使用。重试原 POST 就能找回原任务，无需另造一个危险动作。

本轮新增 `blocksInstance:boolean` 与 `reviewSummary:{id,status,resultCode,appliedAt}|null`。锁按中央实际 `(instanceId,taskId)` 计算，不从 UNKNOWN 或最近 100 条任务推断。targets 的锁字段显式返回 null 或真实阻塞任务 ID/`INSTANCE_HAS_UNRESOLVED_TASK`；被锁目标 `allowedActions=[]`，仍可按 ID 打开列表之外的原任务。

`canControl` 与全局 allowedActions 表示授权能力，不因所有授权实例都有锁而消失。`targets[].canConfirmPending` 是原键查询的显式授权，仍受操作角色、目标名单、模式和全局只读等约束。前端新动作同时要求无锁和 allowedActions；只有已保留的未确定原意图，且当前实例仍存在、中央节点和 Agent 局部 ID 及来源模式与原意图一致，才能按 canConfirmPending 重送原键。已知绑定变化或未知来源时禁用，不能通过更换键绕过锁。

操作前展示确认框，提交成功只表示任务被接收。断网或超时保留原幂等键，提示结果待确认；UNKNOWN 不出现自动重试按钮。切换任务或退出登录必须使旧请求失效。旧演示成功与 Agent 模拟成功都不代表 Docker 已操作。

## 操作权限与开关

- API 查看令牌为 `ARGUS_API_ACCESS_TOKEN`，操作令牌为独立的 `ARGUS_API_CONTROL_TOKEN`；仍使用同一个 Bearer 头。开启 API 认证时，查看令牌不能调用任何写接口，包括旧节点/实例维护接口。操作令牌可读取。操作人由服务端记为 `operator`，不接受浏览器伪造 actor。
- 中央任务开关 `ARGUS_TASK_CONTROL_ENABLED=false`，中央实例允许列表 `ARGUS_TASK_ALLOWED_INSTANCE_IDS`，真实 Docker 开关 `ARGUS_TASK_ALLOW_DOCKER=false`。开放任务要求 API 认证、非空且不同的两个令牌，以及 Agent 读取网关、主机白名单、独立 Agent 控制令牌和 `ARGUS_AGENT_GATEWAY_ALLOW_CONTROL=true`。旧 GET 网关仍保持 `read-only=true`，全局 API 只读仍优先。
- Agent `control.enabled=false` 保持默认。`ARGUS_AGENT_CONTROL_TOKEN` 与读取令牌不同，POST/GET tasks 使用控制令牌；`ARGUS_AGENT_CONTROL_INSTANCES` 是允许控制的 Agent 局部 ID 列表，发现到容器不等于得到操作权限。
- 中央提交、实际投递、Agent 接收和执行前均重查相应配置。关闭任务开关后仍可查询已保存结果，操作令牌提交已有幂等键也只找回原任务，不创建新命令；全局 API 只读则仍拒绝 POST。以上是令牌角色与目标授权的基础，不宣称完整用户/项目 RBAC。

## 中央与 Agent

Agent health 保留采集协议 1.1，新增 `taskProtocolVersion:"1.0"`、`storeId`、`executionMode:"MOCK|DOCKER"`、`controlEnabled`。storeId 属于持久 Inbox，普通进程重启不变，丢失或替换目录时改变。只读部署无 Inbox 时 storeId 可为 null；不具备完整任务契约不得接收控制。

POST `/api/agent/tasks` 正文仅包含以下字符串字段；严格拒绝缺项、重复键、未知键、嵌套或尾部垃圾：

```json
{
  "commandId": "<UUID>",
  "instanceId": "<agent-local-id>",
  "action": "restart",
  "expectedNodeId": "<agent-reported-node-id>",
  "expectedStoreId": "<persistent-inbox-id>",
  "expectedExecutionMode": "MOCK",
  "expiresAt": "2026-10-08T15:00:00Z"
}
```

首次持久化接收返回 202；相同 commandId 与完整相同请求返回 200 原任务；冲突返回 409。过期或不匹配的节点、Inbox、执行模式不得执行。GET `/api/agent/tasks/{commandId}` 200 返回持久记录，不存在返回明确 404。Task 响应为 `taskId/instanceId/action/status/message/createdAt/startedAt/finishedAt/executionMode/nodeId/storeId/resultCode/observedStatus`；身份、模式和状态均须由中央验证，不能只看 HTTP 200。

Agent 固化解析后的目标容器名称和执行模式。PENDING 恢复时不因别名或 MOCK 配置变化而变为另一种操作；每个实例最多一个未决任务，UNKNOWN 也保持互斥。当前实例按容器名称识别，尚未绑定 Docker 物理容器 ID；删除并以同名重建容器属于这一身份边界。执行前确认截止时间，持久保存 RUNNING 后、最终容器发现完成后，在副作用入口前分别复查期限；成功必须核验目标的实际状态，命令超时、中断或可能已产生副作用但无法核验时为 UNKNOWN。

## 持久化与恢复

中央事务一起写任务、投递队列、实例互斥和追加事件。调度使用数据库租约与随机领取标识进行条件更新，HTTP 在事务外执行；旧 worker 的迟到结果不能覆盖已被重新领取或已结束的任务。历史任务不能随节点删除丢失，有任务历史的节点删除返回 409。

首次投递前绑定 Agent 的节点标识、storeId、执行模式和目标地址。每轮先验证绑定，再按 commandId 查询；同一 storeId 下明确 404，且中央未保存 Agent 已接收的证据时，才允许用原请求重投。已确认接收后记录却消失，必须进入 UNKNOWN，不能重放；接收证据与状态一起持久化，经过 RETRY_WAIT 也不丢失。storeId/目标变化、Agent UNKNOWN、超过确认期限等进入 UNKNOWN，停止投递，不自动创造新命令。关闭控制停止新投递，但允许查询已接收命令；UNKNOWN 不自动释放互斥。本轮独立人工核对以不可变原记录、人工依据和有效 Agent 回执为前提，中央 APPLIED 事务只条件解除原锁；详见独立核对契约，生产尚未启用。

HTTP 响应正文有大小上限，完整响应异步任务另设连接加读取的总截止时间，超时取消请求和正文订阅。租约大于本轮三次完整 HTTP 请求预算；不能仅依靠 JDK 请求超时来约束响应头之后的慢正文。返回成功还必须有合理的开始/结束时间，以及 STOP 对应 STOPPED、START/RESTART 对应 RUNNING 的观测证据；缺失或矛盾证据按 UNKNOWN 处理。

Agent 用独占目录锁、每条任务原子文件替换及文件同步保存 Inbox。无原子替换能力、损坏记录或落盘失败必须停止新执行。持久化 PENDING 可恢复排队，重启发现 RUNNING 则记 UNKNOWN，绝不重放。终态持久化后重复查询返回原结果；不能随意删除旧 Inbox 来回收容量。容量到限后拒绝新任务，已有任务仍可查。

恢复旧备份可能使较新的命令消失，却仍保留旧 storeId；目前没有防磁盘回滚机制。因此 Inbox 备份恢复必须先关闭控制、人工核对未决任务，不能把旧目录覆盖后沿用原身份直接重新投递。更换恢复身份会令中央旧任务进入 UNKNOWN，而不是据“查不到”推断可以重做。

保证范围是重复传输去重与保守的进程崩溃恢复，不承诺 Docker 副作用 exactly-once 或所有平台断电后的磁盘一致性。Windows 目录 fsync 有平台边界，文件/目录损坏与灾难恢复需要独立演练。

底层行为参照 JDK 17 的 [FileChannel.force](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/channels/FileChannel.html#force(boolean)) 与 [Files.move](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...))：存储同步保证依赖本地文件系统与操作系统；不支持原子移动时会抛出异常。因此实现必须报告写入失败，不能退回可能留下半份记录的普通覆盖。

## 验收要求

1. 双节点同名实例的控制与结果不串线，操作令牌和目标允许列表生效。
2. 并发重复请求只产生一条任务、一个命令，冲突内容与同实例未决命令被拒绝。
3. 中央提交后重启可继续处理；Agent 终态可重查；RUNNING 崩溃或 Inbox 身份变化不会重放重启动作。
4. 网络丢失、队列满、到期、磁盘错误和不合法响应有明确状态；旧结果不能覆盖新状态。
5. 任务成功不伪造观测状态，MOCK/DOCKER/LEGACY_MOCK 的来源清晰。
6. 含旧数据的 H2/MySQL V4→V5 迁移保留任务，旧演示任务不生成投递。
7. 默认只读仍生效；仅本机 mock 和隔离测试进程可开启本轮控制验证，生产及真实游戏容器不操作。
