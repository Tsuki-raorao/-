# Argus Java 后端面试拷打文档

这份文档用于面试演练。项目可以这样介绍：Argus 是一个面向多节点服务器和 Minecraft/Docker 服务的运维控制台。Agent 负责采集主机、容器和日志，Java 控制中心负责资源目录、任务编排、幂等、状态机、权限边界和审计，Vue 管理台负责展示与人工确认。当前已完成采集、任务队列、Agent Inbox、UNKNOWN 保护、人工核对、项目成员权限、MySQL 迁移，以及可选的 Redis 热状态缓存和 RabbitMQ 任务事件通知；真实 OIDC 注册和 AI/RAG 属于后续演进。

面试时不要把“设计过”说成“已经上线”。遇到尚未接入的能力，直接说明当前版本的边界、为什么没有提前引入，以及下一步的替换点。

## 一、项目与架构

### 1. 你先用一分钟介绍这个项目

Argus 是多节点服务器运维平台。控制中心用 Spring Boot 提供 REST API 和任务编排，Agent 部署在被管理服务器上，负责 Docker/主机采集和受控执行，MySQL 保存资源、任务、事件和核对事实，Vue 管理台展示状态。核心目标不是发一个 shell 命令，而是让一次操作具备目标身份、幂等键、状态流转、超时、重试和审计证据。

### 2. 为什么采用 Controller、Service、Repository 分层？

Controller 只处理协议、参数和 HTTP 状态；Service 负责业务规则和事务边界；Repository 负责 SQL、映射和兼容旧表结构。这样任务状态机、权限检查和持久化不会全部堆在 Controller 中，也便于用 Service 测试业务分支。

### 3. 控制中心和 Agent 为什么要分开？

控制中心是控制面，保存全局事实、权限和任务；Agent 是数据面，接触本机 Docker、进程和日志。浏览器、数据库和未来的 AI 都不能直接访问 Docker socket。分离后可以限制 Agent 权限、隔离故障，并允许不同服务器使用不同的采集适配器。

### 4. 一次重启任务的完整链路是什么？

网页先读取实例能力和互斥状态，提交带 `Idempotency-Key` 的请求；控制中心校验令牌、目标、执行模式和全局开关，事务写入任务及事件；队列 worker 获取租约后把固定 command 投递给 Agent；Agent 先写 Inbox 去重，再执行允许动作并持久化结果；控制中心按 commandId 收回结果，更新任务状态和事件，网页通过查询补偿最终状态。

### 5. 为什么任务不能直接同步调用 Agent？

同步调用会把网页请求和远端 Docker 操作绑定在一起，网络超时后无法判断动作是否已经发生，也无法可靠重试。持久任务队列把“请求已接收”和“执行结果已确认”分开，客户端断线后可以按任务 ID 查询，不会因为超时就重复执行。

### 6. 项目中哪些数据是事实源？

MySQL 是任务、任务事件、人工核对、权限和资源目录的事实源；Agent Inbox 是 Agent 侧的去重和恢复事实；实例快照是最近观测，不等于任务结果。Redis 将来只做短期状态、限流和广播，不能替代任务或审计事实。

### 7. 为什么没有让前端直接连接 Agent？

这样会绕过项目权限、任务审计和中央状态机，也会把 Agent 地址和凭据暴露给浏览器。前端只访问控制中心，控制中心按项目和目标授权后再通过 Agent 协议执行。

### 8. 新增一种服务器类型如何接入？

先实现统一 Adapter 契约，声明实例发现、健康检查、指标、日志和动作能力；Agent 注册能力和版本，控制中心保存能力快照；通用页面只展示支持的字段，不支持的指标返回 null 和明确状态。任务编排只依赖标准动作和能力，不把 MySQL 或 Minecraft 的细节写进核心流程。

## 二、Java 与 Spring

### 9. Spring Boot 启动时做了什么？

启动主类创建 ApplicationContext，扫描 Controller、Service、Repository 和配置类，绑定 `@ConfigurationProperties`，初始化数据源、Flyway 和安全过滤链，迁移完成后执行演示数据或本地身份夹具。生产配置通过环境变量注入，默认关闭演示写入。

### 10. `@Component`、`@Service`、`@Repository` 有什么区别？

它们都是组件扫描的候选类，但语义不同：Service 表示业务服务，Repository 表示持久化边界，Repository 还可以获得 Spring 的数据访问异常转换。用语义标注让结构和维护责任清晰，而不是全部使用 Component。

### 11. `@Transactional` 应该放在哪里？

放在 Service 或专门的事务组件上，覆盖“校验版本、写状态、写事件、写审计”的完整事实变更。查询通常不需要长事务。要注意同类内部自调用不会经过代理，因此需要通过外部 Bean 调用或重构事务边界。

### 12. 事务提交后再投递 Agent 的问题是什么？

如果数据库提交成功但进程在投递前崩溃，任务会停在待处理；如果先投递再提交，数据库可能没有这条任务事实。当前通过持久队列和 worker 重扫解决，后续可以用 Outbox 让“事实写入”和“消息发布”更明确地解耦。

### 13. Spring Security 在项目中负责什么？

负责请求认证、会话或 JWT 的解析、CSRF 和登录回调边界；项目授权仍由业务层根据当前用户、项目和权限二次检查。认证通过不代表能访问任意节点，也不能把前端传来的 userId 当成可信身份。

### 14. 为什么 API 返回统一的 `ApiResponse`？

统一成功数据、错误码和消息格式，前端可以集中处理 401、403、409 和 5xx。业务错误使用稳定机器码，例如版本冲突、目标不存在、任务互斥，而不是让前端解析异常堆栈。

### 15. 如何处理参数校验和错误映射？

入口校验格式、长度、枚举和必填字段；Service 校验业务前置条件；全局异常处理器把业务异常映射为固定 HTTP 状态和机器码。不能把异常吞掉后返回空列表，否则前端会把失败误认为“没有数据”。

### 16. Java 17 在项目中体现在哪里？

使用 record 表达不可变 DTO/事件、增强的 switch 和标准 HttpClient/时间 API。领域对象仍保留必要的可变状态以兼容持久化和状态机，但跨层传递的数据尽量使用不可变结构。

### 17. `Instant` 和本地时间怎么选？

数据库事件和任务时间使用 UTC 语义的 `Instant`，展示层按用户时区格式化。不要在后端把服务器默认时区写进业务判断，否则跨节点部署会出现任务过期和排序差异。

### 18. 如何避免线程池被慢 Agent 请求拖垮？

采集、任务 worker 和 Web 请求使用有界线程池，远端请求有连接和读取超时；单实例任务按实例串行，避免同一目标并发执行。失败进入明确状态和退避，不无限创建线程或无限重试。

## 三、数据库与并发

### 19. 为什么使用 Flyway？

数据库结构变化必须可追踪、可重复验证和按版本部署。旧迁移不改写，新结构追加版本；上线前在隔离 MySQL 恢复备份并按顺序执行迁移，失败时按备份和回滚方案处理。

### 20. V6/V7 迁移最容易出现什么问题？

旧表列类型、字符集、排序规则和外键必须保持一致；MySQL utf8mb4 的联合索引可能超过 InnoDB 长度限制。项目在 V7 中使用生成的 SHA-256 identity_hash 做唯一约束，并在隔离 MySQL 上验证 V6→V7。

### 21. 为什么需要乐观锁？

项目成员和项目名称修改都带 `expectedVersion`。更新条件同时匹配 ID 和版本号，影响行数不是 1 就返回冲突。这样两个管理员不会静默覆盖对方的权限修改。

### 22. 如何保证最后一名管理员不能被删除或降权？

在同一事务中锁定身份配置闸门和相关用户/项目，再统计有效管理员；若变更后会变成零管理员，返回固定 409。前端按钮只是体验，真正保护必须在服务端重新判断。

### 23. 任务幂等键如何实现？

客户端为一次明确操作生成 UUID，服务端按作用域和幂等键查已有任务。相同键和相同正文返回原任务，不创建第二条；同键正文不同返回冲突。结果未知时只查询原键，不能生成新键掩盖第一次请求。

### 24. 为什么还要保存 requestHash？

幂等键只能标识请求名，不能证明正文没有被替换。服务端对规范化正文计算哈希并保存，重试、人工核对和重新授权都必须匹配原哈希，防止把一个授权套到另一条命令上。

### 25. 如何处理同一实例的并发任务？

中央任务锁和 Agent Inbox 都按实例身份加互斥。创建、投递、回执和人工核对时重新读取权威锁；任何一层发现已有未决任务都拒绝新动作。旧任务完成后，新的操作必须使用新的 commandId。

### 26. 为什么不能把 UNKNOWN 直接改成 FAILED？

UNKNOWN 表示中央不知道远端动作是否发生，改成 FAILED 会丢失安全事实，可能导致重复启动或重启。项目用独立人工核对记录读取 Agent 证据，满足条件后只解除原互斥，原任务仍保持 UNKNOWN。

### 27. 任务状态机如何防止非法跳转？

所有状态变化经过 Service 的允许转换和版本号检查，并追加不可变事件。worker 只能提交与 commandId、attempt 和当前版本匹配的结果；迟到结果不能覆盖更新后的权威状态。

### 28. MySQL 迁移为什么不能只在 H2 验证？

H2 对索引长度、字符集、外键和 DDL 事务语义的行为可能不同。项目的普通测试使用 H2 提速，同时保留隔离 MySQL 专项，迁移前用真实备份恢复到独立数据库验证。

### 29. 查询最近 100 条任务有什么隐患？

只按时间排序可能遇到同一时间戳的顺序不稳定，因此使用 `created_at DESC, id` 作为稳定排序。生产还需要分页、索引和按项目过滤，不能让审计查询扫描全表。

### 30. 如何避免 SQL 注入？

所有用户输入通过 JdbcTemplate 参数绑定，表名和排序字段不接受用户拼接；动态条件使用固定白名单。日志和错误消息也不能把完整 SQL 或令牌返回给客户端。

## 四、可靠任务与 Agent

### 31. Agent Inbox 解决什么问题？

它记录已接收 commandId、目标、状态和结果。中央因网络超时重复投递时，Agent 先按 commandId 去重，返回已有结果，不再次执行 Docker 动作。

### 32. “恰好执行一次”能做到吗？

跨网络和 Docker 外部副作用不能轻易承诺 exactly-once。项目承诺的是请求幂等、Agent 接收去重、状态可恢复和危险操作不自动重放，并明确把外部副作用的不确定性暴露成 UNKNOWN。

### 33. Agent 为什么要同时校验 nodeId、storeId 和 instanceId？

instanceId 只在中央范围内唯一，nodeId 和 storeId 用来证明当前 Agent 身份和持久 Inbox 没被替换。三者不匹配时拒绝命令，防止把一个节点的任务投到另一个节点。

### 34. Agent 失联时中央怎么处理？

请求保留在持久队列，worker 按租约和退避重试；网页显示“已接收/等待结果”，不会直接显示失败。超过策略窗口后进入明确的超时或 UNKNOWN 语义，仍保留原 command 和审计事件。

### 35. 如何防止迟到回执覆盖新状态？

回执必须匹配任务 ID、commandId、attempt、节点、实例、执行模式和当前版本。任何字段不一致都记录拒绝原因，不更新实例快照和任务事实。

### 36. 为什么采集失败不能把指标写成 0？

0 是有效观测，失败是未知；把失败写成 0 会误导告警和面试演示。模型使用可空数值、来源、采样时间和 `metricsStatus` 区分 AVAILABLE、PARTIAL、UNAVAILABLE 和 UNKNOWN。

### 37. Docker 容器名为什么不能作为唯一身份？

不同节点可以有同名容器，容器重建后名称也可能复用。控制中心使用中央实例 ID，并保存 nodeId、agentInstanceId 和实际 container name 的绑定；日志和任务都按中央 ID 查询。

### 38. 远端命令执行如何限制风险？

动作使用固定枚举和目标白名单，不接受任意 shell；Agent 对实例名、动作、模式和过期时间做校验，控制开关默认关闭。后续 Adapter 也必须提供动作白名单、超时和回滚语义。

### 39. 日志为什么不直接持续写 MySQL？

日志正文量大且写入频繁，数据库不适合作为长期日志流。当前版本保存有限摘要并按实例查询；生产演进可用 Loki/对象存储保存正文，MySQL 只保存索引、任务和审计摘要。

### 40. Prometheus 在系统里负责什么？

Prometheus 负责拉取时序指标，控制中心和 Agent 暴露受保护的 metrics；MySQL 保存业务事实和告警事件，不保存每次采样的全部原始时序。指标标签不能放玩家名、命令正文等高基数字段。

## 五、权限、审计与面试追问

### 41. 认证和授权有什么区别？

认证回答“你是谁”，授权回答“你能对哪个项目的哪个资源做什么”。项目的认证骨架支持旧令牌和未来 OIDC，但所有项目资源仍由服务端按项目成员和权限再次校验。

### 42. 为什么不能相信前端传来的 projectId？

projectId 只是查询范围提示，服务端必须根据当前主体重新读取成员关系和项目状态。没有 `RESOURCE_READ` 返回 403；没有项目范围的请求在身份模式下直接拒绝。

### 43. 审计记录至少要保存什么？

操作者、项目、资源类型和 ID、动作、前后状态摘要、结果码、时间、请求键和必要的证据摘要。不能保存密码、私钥、Cookie、访问令牌或完整请求头；人工证据还要按项目权限限制读取。

### 44. 为什么 202 不代表任务成功？

202 只表示请求已持久接收，后续还要经历排队、投递、执行和回执。前端必须通过任务查询和事件时间线展示最终状态，不能收到 202 就把实例标成成功。

### 45. 如果数据库写成功、HTTP 响应丢失怎么办？

浏览器保留原幂等键和最小恢复引用，重载后先 GET 原键对应记录；找到记录就结束本地不确定状态，找不到也不能自动换新键重做。服务端保证同键同正文不会重复创建。

### 46. Redis 为什么不是第一版事实源？

Redis 适合 TTL、限流、短缓存和广播，但丢失后不能恢复任务事实和审计。第一版用 MySQL 持久队列保证正确性，规模上升后再让 Redis 承担高速协调，并保留 MySQL 回放路径。

### 47. 如果要支持高并发，你会怎么改？

先按项目、实例和时间建立索引，任务写入使用连接池和有界队列；再用 Outbox/RabbitMQ 解耦投递，用 Redis 做短锁和热点状态，worker 按实例分片并限制租约。压测要覆盖重复请求、迟到回执、Agent 断线和数据库故障，而不是只测 QPS。

### 48. AI Agent 接入后如何防止越权？

AI 只能读取当前用户和项目授权范围内的指标、日志、配置和审计；工具层再次检查 scope。涉及写操作只生成带证据的 ActionPlan，由人或审批策略确认后交给现有 Task Orchestrator，模型不能直接访问 Docker。

### 49. 这个项目最大的技术风险是什么？

远端动作的外部副作用无法做到绝对 exactly-once，以及权限模式切换和迁移期间的兼容性。应对方式是持久队列、Inbox 去重、版本/CAS、UNKNOWN 保护、隔离迁移演练和默认只读，而不是用“请求超时即失败”掩盖不确定性。

### 50. 如果让你继续做三个月，你的优先级是什么？

第一阶段完成审计查询、Adapter 能力协商、Minecraft TPS/MSPT 采集和告警演示；第二阶段接入 Redis/RabbitMQ、多副本和故障压测；第三阶段接入真实 OIDC、凭据轮换、生产灰度和 AI/RAG。每阶段都先补接口契约、迁移、测试和回滚证据，再扩大运行范围。

## 面试结束时的项目收口

可以这样收尾：

> 这个项目的重点不是把 Docker 命令包一层 HTTP，而是把一次远程操作变成可授权、可追踪、可恢复的业务事实。控制中心保存任务和审计，Agent 负责本机执行，幂等键和 Inbox 解决重复投递，UNKNOWN 保护解决网络不确定性，项目权限保证资源边界。当前版本已经完成核心链路，登录、消息中间件和 AI 是下一阶段的工程化增强。
