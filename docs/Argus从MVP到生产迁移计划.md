# Argus 从 MVP 到生产版迁移计划

更新时间：2026-09-29  
状态：设计基线，尚未进入代码改造

## 1. 当前 MVP 与目标版的差距

当前版本已经有 Spring Boot 控制中心、Vue 管理台、Java Agent、MySQL/H2 持久化和基础节点/实例/任务/日志 API，但 Agent 默认使用模拟执行器，缺少 Redis、消息队列、认证、实时推送、指标和高可用。

目标版需要形成三条独立管道：

1. **命令管道**：MySQL Outbox → RabbitMQ → Agent → 幂等结果。
2. **状态管道**：Agent 心跳 → Redis TTL → 批量快照和告警。
3. **观测管道**：指标 → Prometheus；日志 → Loki/对象存储；页面 → WebSocket。

不进行一次性大重写，保留现有 REST API 作为兼容入口，逐步把实现替换到新模块和新事件契约。

## 2. 阶段和退出条件

### P0：设计冻结

内容：确定领域模型、Agent 协议版本、任务状态机、权限模型、数据保留、容量目标和威胁模型；记录 ADR，冻结 API 和事件契约。

退出条件：`desired/observed`、任务状态迁移、错误码、重试规则和数据责任没有未决冲突；文档评审通过。

### P1：企业化数据底座

内容：将控制中心整理为模块化单体；扩展用户、项目、角色、Agent 凭据、任务尝试、任务事件、Outbox、审计表；补充 CAS、版本号、索引、分页和密钥外置。

退出条件：迁移可重复执行；任务和状态事件有完整时间线；没有明文凭据；旧 API 的基础查询仍可用。

### P2：Redis 和可靠异步任务

内容：加入 Redis 在线租约、实例互斥、限流和幂等短键；加入 RabbitMQ 命令队列、ACK、重试、死信、Outbox Relay 和 Agent Inbox；把 Mock Executor 抽象成真实 Docker Executor 的接口。

退出条件：模拟 1000 个 Agent 每 10 秒心跳持续 30 分钟，错误率低于 1%；任务突发 100 次/秒时没有重复副作用；控制中心或 Agent 重启后未完成任务可恢复。

### P3：实时和可观测性

内容：Agent Gateway/WebSocket、断线补偿、Prometheus、Grafana、Alertmanager、Loki 或对象存储日志；建立指标标签和日志保留策略。

退出条件：心跳离线、任务超时、磁盘不足、容器停止能够产生并恢复告警；日志突发有背压；WebSocket 断线可以通过 REST 补齐状态。

### P4：安全和权限

内容：Spring Security、OIDC/JWT、租户/项目级 RBAC、Agent mTLS 或短期令牌、凭据轮换、命令白名单、审计和网络隔离。

退出条件：越权、重放、过期令牌和错误项目访问全部拒绝；凭据轮换不中断正常 Agent；3306、Redis、MQ 不直接暴露公网。

### P5：高可用和压力验证

内容：控制中心无状态多副本；RabbitMQ quorum；Redis Sentinel/Cluster；MySQL 备份、恢复和可选只读副本；加入 k6/Gatling 压测与故障注入。

退出条件：控制中心滚动发布不丢任务；单个 API 实例、MQ 节点、Redis 节点或网络链路故障后可以恢复；目标 RPO ≤ 5 分钟、RTO ≤ 15 分钟；月可用性目标 99.9%。

### P6：AI 只读诊断

内容：AI 只调用指标、日志、变更和事件查询工具，保存证据、结论和不确定性；生成的方案必须经过权限、前置条件和人工确认，再复用 Task Orchestrator 执行。

退出条件：AI 无法访问无权限实例；没有证据时明确表示未知；AI 不能跳过任务状态机直接操作 Agent。

## 3. 按节点角色安排落地顺序

先在测试环境验证功能链路，再依据容量评估分配节点。下列为通用部署角色，不代表现网机器数量、厂商、容量或状态，也不构成高可用承诺：

- 工作负载节点：保留业务服务，只部署经过资源评估的轻量 Agent。
- 控制节点：承载网站和控制中心；部署消息队列、指标或日志组件前评估 CPU、内存、磁盘和保留策略，资源不足时拆分或扩容。
- 数据库节点：承载 MySQL 和受控备份，限制数据库访问来源并验证恢复流程。

企业版可使用独立节点或托管 Redis、RabbitMQ 和 MySQL。控制中心和 Agent 的协议先在测试环境验证，资源和故障恢复条件满足后再切换多副本部署。实际节点清单和容量报告仅保存在受控运维档案中。

## 4. 压测与故障演练清单

- 1000 Agent × 10 秒心跳，观察 Redis P99、API CPU 和 MySQL 写入量。
- 任务突发、重复投递、乱序结果和旧 fencing token 回报。
- 控制中心重启、MQ 重启、Redis 重启、Agent 断网和网络抖动。
- 日志持续流和 10 倍突发，观察队列积压、压缩、丢弃和恢复。
- 同一实例同时提交启动、停止、重启，确认互斥和最终状态。
- MySQL 备份恢复，验证 RPO/RTO 和 Outbox 未发布事件。
- 令牌过期、节点证书吊销、跨项目访问和重放请求。

## 5. 设计决策

- **先模块化单体，后按瓶颈拆服务**：避免在没有容量数据时增加部署复杂度。
- **RabbitMQ 负责可靠命令，Kafka/Redpanda 留给高量日志和遥测**：两类数据的保序、重试和留存需求不同。
- **Redis 不是事实数据库**：Redis 只存可重建的高速状态，任务和审计最终以 MySQL 为准。
- **至少一次投递 + 幂等执行**：不把 exactly-once 当作宣传口号。
- **AI 最后接入**：AI 只能读数据和生成建议，执行必须复用权限与任务系统。
