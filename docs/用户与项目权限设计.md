## 1. 本阶段解决什么问题

当前控制中心使用全局读取令牌、操作令牌和只读开关，没有用户账号、项目成员及逐资源授权。已完成的可靠命令、UNKNOWN 人工核对、Agent 持久记录和隔离真实 Docker 验收，为执行可靠性提供基础，但不能替代多用户权限。

本阶段让每次查看、操作、核对和成员变更都能回答：谁发起、属于哪个项目、当时是否有权、后来是否撤权、发生了什么。生产保持只读，控制与人工核对开关仍关闭；设计及本地实现不会自动开启生产控制。不涉及聊天中转项目。

| --- | --- | --- | --- |

## 2. 身份入口

### 2.1 网页登录：BFF 与 OIDC

网页通过 Spring Security 的 OIDC 授权码登录，中央作为 BFF 保存身份提供方令牌。浏览器只持有会话 Cookie，不把访问令牌长期存入前端存储，也不接收 Agent 凭据。OIDC 登录扩展应使用框架提供的认证链路。[Spring Security OAuth2 Login](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/advanced.html)

本项目要求显式验证 state、nonce 和 PKCE S256；登录回调、退出后跳转及允许的外部 origin 固定配置，不能由任意 Host／转发头或请求参数决定。仅信任已配置的反向代理。会话 Cookie 使用 HttpOnly，生产使用 Secure，并验证 SameSite 设置与实际回调兼容；登录后更换会话标识，退出使本地会话失效。

凡接受 Cookie 身份的写请求均启用 CSRF 防护，包括退出和成员管理；CORS 允许来源不能代替 CSRF。无 CSRF 例外可覆盖命令或人工核对入口。仅完全不接受 Cookie 身份的外部无状态 API，才可按明确匹配范围考虑豁免。[Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)

### 2.2 外部调用：JWT Resource Server

外部 API 使用 Spring Security Resource Server 验证访问 JWT，至少校验签名、固定 issuer、预期 audience、有效期及允许的签名算法。可信 JWKS 地址来自服务配置；不根据任意来访令牌指定地址下载密钥。不接受 ID Token 充当 API 访问令牌。[Spring Security JWT Resource Server](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

用户唯一身份是经过验证的 `(issuer, subject)`，邮箱仅作为展示信息。不同身份提供方或不同 subject 即使邮箱相同，也不能自动合并。令牌中的角色声明、前端传入的角色和用户 ID 都不能直接赋予本地权限；本地启用状态与角色以数据库为准。

启用新身份模式后，旧共享令牌、匿名请求及旧配置中的放行分支不得成为备用认证。身份提供方故障、验证失败或配置缺失须关闭访问或启动失败。Cookie 与 Bearer 同时出现时，必须有明确且可测试的规则，不能验证失败后悄悄换另一种身份。

身份提供方停用账号不等于已经签发的 JWT 立即失效。本地禁用用户／撤销成员关系必须及时阻止后续本地授权；远端账号撤销的延迟，需按令牌寿命和采用的撤销机制明确说明。不得承诺尚未实现的即时远端撤销。

### 2.3 版本与实现约束

使用 Spring Security 的过滤器链及统一服务授权，不自制密码登录或生产 JWT 签发方案。依赖版本与本项目 Spring Boot BOM 对齐，先验证对应版本的接口及安全配置，不能直接照搬新版文档示例并同时未经评审升级运行时。身份提供方选型、生产客户端注册及证书配置另行确认。

## 3. 角色与项目边界

下表是已冻结的第一阶段职责和角色边界；更细的组织／租户角色仍属后续范围。

| 职责 | 可以做什么 | 必须保留的限制 |
| --- | --- | --- |
| 平台管理员 | 管理用户启停、项目及平台授权、执行明确的旧资源接管 | 不绕过全局只读、Agent 名单或独立控制／核对开关；平台管理权不自动等于任意业务操作权 |
| 项目管理员 | 管理本项目成员与允许授予的项目角色 | 不能授权其他项目、授予平台管理员或扩大自身管理范围 |
| 项目操作人员 | 在所属项目内执行明确允许的控制、独立人工核对 | 每个入口、后台投递和核对解锁都重新检查当前授权及门禁 |
| 项目只读成员 | 查看获授权项目的节点、实例、采集与允许展示的历史 | 不能创建命令、人工核对、管理成员或修改节点绑定 |
| 无成员关系的已认证用户 | 查看自己的登录状态及明确允许的公共信息 | 默认没有业务资源，空项目集合不能解释为查看全部 |

第一阶段采用一个节点归属一个项目、自动发现实例继承节点项目的边界。不能一方面让项目成员读取整台 Agent 的原始实例列表，另一方面声称同一节点上的其他项目实例已被隔离。更细的实例共享与跨项目节点复用不在本阶段默认开放。

平台管理与业务访问分别判断。角色、项目、资源 ID、真实操作者均由服务端决定并验证；未知 JSON 字段或客户端传入的管理字段不能导致批量赋值提权。资源详情对无权用户应避免暴露存在性，角色不足与资源不可见的错误策略需统一。

项目过滤必须进入数据库查询，早于排序、数量限制、分页和聚合。不能先获取全局最近 100 条再在 Java 中过滤；列表总数、锁拥有者、能力列表和错误响应也不能泄露其他项目。后台采集采用受限系统职责，不依赖网页请求的线程上下文，也不因此向用户提供系统级访问。

## 4. 现有入口的权限覆盖清单

以下列的是当前入口类别，用于防漏；没有在此冻结新增 API。

| 当前入口／资源 | 必须实施的边界 |
| --- | --- |
| 健康检查 | 可以公开最少探活信息；不附带项目、实例、用户或凭据详情 |
| 节点和实例列表、单项详情 | 项目授权在查询前生效；通过节点 ID 或实例 ID 的替代路径结果一致 |
| 实例日志及不指定实例的日志列表 | 仅汇总获授权项目；省略参数、空字符串、空项目集合不能转为全局日志 |

| 原始 Agent 网关健康、实例、日志 | 限定系统诊断或按完整节点项目授权；禁止绕过中央实例映射读取别人的日志 |
| 节点创建、删除、心跳及地址绑定 | 明确的管理／接入职责；保留目标主机限制和身份绑定，防止伪造心跳或重复接管另一 Agent |
| 后续用户、项目、成员及审计入口 | 默认拒绝；限制授予范围、最后管理员保护、审计读取范围及修改审计 |

特别需要纠正的现有集成点：全局幂等键查询早于资源授权、可选日志参数退回全局、全局能力列表、任务发起人固定写为 `operator`、worker 使用固定操作权限布尔值。这些适用于旧共享令牌模型的实现，不能原样作为新多用户授权。

## 5. 撤权与异步执行的准确语义

### 5.1 新命令的投递许可

撤权无法撤回已交给 Agent 的动作。短事务提交和随后 HTTP 发送也不可能自动成为同一个原子操作。本阶段采用以下可验证的线性化边界：

1. worker 在每次拟发送新的命令 POST 前，进入短事务，锁定当前用户、项目及成员授权所需记录，重验身份状态、项目权限、操作门禁和队列租约，并持久记录本次投递许可。
2. 禁用用户／撤销成员关系使用相同的授权锁及一致的顺序。撤权事务完成后，不得再产生新的投递许可。
3. 撤权前已提交的许可视为可能在途，即使实际网络发送稍后发生，也不能宣称被撤回。HTTP 不在数据库长事务内执行。
4. 未获过投递许可的任务可明确取消后条件释放自己的锁；已有许可却无法确认结果时保留不确定状态和互斥。允许 GET 查询原命令事实并收敛，不能因 GET 404 而在撤权后重新授权 POST。

租约、任务状态和投递许可须在同一短事务内相互校验，晚到 worker 不得使用过期租约获得许可。前端会话退出不删除已经受理的操作；后台不保存人类 Bearer 令牌来维持任务权限。

### 5.2 人工核对的撤权与重新授权

人工核对依然是独立权限和独立开关。Agent 已持久 CLOSED 回执，并不保证中央此时仍有权解除自己的锁。中央最终应用回执、写入审计和条件释放原任务锁，必须在同一短事务中再次验证当前核对授权，并与撤权操作按相同锁规则串行。

如果撤权先完成，中央保留原锁并显示阻塞原因；只能查询已有事实，不自动以系统身份代替原核对人继续。必须提供明确的重新授权路径，不能因原发起人离职留下永久死锁：可由恢复权限的原核对人，或另一名有权人员明确接管这次核对，在重新阅读证据并确认风险后继续。

接管产生独立的授权人与审计记录；原发起人、原理由、证据摘要、请求哈希、固定 resolution ID 和 Agent 请求内容保持不变。已有 Agent 回执通过查询复用，不为接管生成新的原动作。当前接口为 `POST /api/task-resolutions/{id}/authorizations`，使用新的 `Idempotency-Key` 和 `expectedRequestHash`，并提供按新键查询接口；页面尚未接入。查询或重试旧回执不得删除后来新任务持有的锁；条件释放始终绑定原任务。

### 5.3 锁顺序与管理操作

身份管理、项目成员变更、任务提交、投递许可、核对续办及最终解锁必须使用同一授权实现及书面锁顺序。队列租约与资源锁的既有顺序需要纳入设计，不能每个模块各加一组 `FOR UPDATE` 后假定没有死锁。

不得以全表管理员权限作为 worker 的真实操作者。记录不可变的原发起人和项目，另记录系统执行职责与后续授权人；重新授权必须是可追踪的明确行为。项目停用、成员撤销和用户禁用都属于授权状态变化。

## 6. 引导管理员、审计及恢复隐私

管理员引导只允许显式配置的 issuer／subject，且一次成功状态持久化。不得让第一个登录者、相同邮箱用户或令牌自称管理员者获得管理员权。重启、更换配置和两个中央同时启动都不能重开引导窗口。

禁用、删除、降权或解绑最后一名有效平台管理员必须被保护；并发处理两位管理员时也不能各自检查后留下零管理员。相关操作使用统一锁，并审计实际执行人、授权变化及结果。项目最后管理人的转移规则需与项目停用流程一并冻结。

审计区分原操作者、系统 worker 与接管人，不能接受客户端自行填写的身份。记录资源归属、动作、结果、时间和必要的变更摘要；不记录访问令牌、Cookie、客户端密钥、私钥、完整请求头或数据库口令。人工核对的理由及现场证据可能包含敏感内容，不能无范围地复制到全局审计列表。

恢复说明、备份和交接包使用公开占位符与私有凭据分离。公开文档和源码不写真实服务器地址、域名、密钥位置或测试令牌；登录恢复链接不携带 Bearer 凭据，网页复制任务／核对参考信息时也不附带认证数据。私有调试证据不进入 Git。

## 7. 旧数据与项目迁移

已有节点、实例、日志、任务、命令和核对历史保留原 ID、关联关系、固定 payload 与哈希。未划分项目的旧资源进入明确的系统管理接管范围，默认不给普通登录用户成员关系，不能自动分给第一个登录者或全部用户。管理员完成核对后执行有审计的接管。

失去父资源的旧历史进入受限的待处理范围，不能为通过查询或外键迁移而删除历史、改写 Agent Inbox 或变成全局可见。旧操作人记为不可登录的历史主体，不伪装成新管理员。

旧队列没有可信用户授权时不能在身份模式切换后自动投递。迁移方案必须明确先停止新投递，核对未决任务，并冻结或显式接管剩余操作；已可能发出的任务仍遵守不确定结果规则。

本阶段不默认开放任意节点跨项目迁移。若后续允许，须先处理未决命令／核对及成员可见性，并保存历史项目归属，不能把过去的任务、日志和证据随当前节点归属一起暴露给新项目。项目停用或删除也不得级联抹除操作审计。

迁移需覆盖已有 MySQL 字符集／排序规则、外键和唯一约束，并在隔离真实 MySQL 与测试数据库验证。任务与核对幂等范围要包含可信项目／操作者关系，避免跨用户泄露；不能因此破坏已经持久的命令、回执和显式接管语义。

## 8. 独立验收矩阵

矩阵中的身份专项仍需补齐接口级和隔离 MySQL 验收；已有基础任务/迁移测试不等于身份模式已通过。外部网络副作用采用隔离服务与可计数测试代理；不以生产控制作为权限测试工具。

| 编号 | 场景 | 必须得到的结果 |
| --- | --- | --- |
| A01 | JWT 错签名、错 issuer／audience、过期、尚未生效、未允许算法、ID Token | 逐项拒绝；不回退为静态令牌或匿名身份 |
| A02 | JWKS 轮换、暂不可达、陌生密钥与伪造密钥地址 | 按可信配置验证并关闭失败路径；不任意联网取钥 |
| A03 | OIDC 错 state／nonce／PKCE、重复回调、伪造外部 origin | 无法建立会话；回调和跳转不能离开允许位置 |
| A04 | Cookie 写请求缺 CSRF、跨站请求、会话固定、退出后旧会话 | 拒绝未授权写入；退出后不能继续以旧会话访问 |
| A05 | 新模式下旧令牌、匿名、Cookie 与 Bearer 混用、无效 Authorization | 规则明确且没有认证降级旁路 |
| A06 | 同邮箱不同 subject／issuer；JWT 自称管理员；客户端填写角色 | 不合并身份、不自动提权 |
| P01 | 无成员身份，空／省略项目或日志过滤参数 | 没有业务资源，不返回全局列表、总数或日志 |
| P02 | A 项目用户遍历 B 项目所有详情、事件、能力、核对与原始网关入口 | 不泄露存在性或内容；拒绝前不向 Agent 发起特权查询 |
| P03 | B 项目超过分页上限，A 项目有较早数据 | A 的授权数据仍能查询；范围过滤先于排序、分页和总数 |
| P04 | 节点、实例、任务及 resolution 的项目／父子关系不一致 | 拒绝混合目标；不能借另一条 ID 路径读取或操作 |
| P05 | 别人的幂等键、同键不同项目／用户、已撤权用户重试旧键 | 不返回别人的结果；不能绕过当前授权或静默接管 |
| P06 | 普通操作人员调用节点创建、心跳、删除、地址接管 | 按管理权限拒绝；目标地址限制和绑定检查仍有效 |
| P07 | 用户退出或切换身份／项目后恢复前端缓存、草稿和待确认请求 | 清除或隔离旧身份数据；禁止用新身份自动提交旧请求 |
| Q01 | 撤权先于投递许可提交 | 不产生新的 Agent POST；从未许可任务安全结束并只释放自身锁 |
| Q02 | 许可已提交后撤权，HTTP 尚未发送／响应丢失 | 记录可能在途边界；允许查原结果，不再获新许可或重复投递 |
| Q03 | 撤权穿插 claim、许可事务、租约过期和晚回包 | 统一锁顺序与 CAS 保证没有旧 worker 越权许可或覆盖新状态 |
| Q04 | 已撤权任务查到 404、项目停用或原操作者已禁用 | 不借重试恢复发送；可能已投递者保留 UNKNOWN 及互斥 |
| R01 | 人工核对投递前撤权 | 不提交新的核对 POST，保留原记录和阻塞原因 |
| R02 | Agent CLOSED 后、中央解锁前撤权 | 中央不得解锁；已有回执与原任务均保留 |
| R03 | 原人恢复授权，或另一有权人明确接管 R02 | 记录新授权，复用原 ID／哈希／回执，不生成或重放原命令 |
| R04 | 旧核对重查／重试与新的实例任务并发 | 不误删新任务锁；没有新增 Docker 动作 |
| R05 | 操作或平台管理员绕过全局只读、核对开关或实例名单 | 仍然拒绝；权限不能覆盖独立业务安全门禁 |
| M01 | 两个登录者与两个中央竞争引导管理员 | 仅固定身份成功一次；持久标记防重启重新引导 |
| M02 | 并发禁用／降权／删除最后两位管理员 | 至少保留一位有效管理员，失败有固定原因和审计 |
| M03 | 项目管理员跨项目授予角色或授予平台角色 | 拒绝；不能通过批量赋值或隐藏字段提权 |
| M04 | 审计读取、错误响应、导出、人工证据和应用日志 | 项目范围一致，无令牌／密钥泄露，身份由服务端确定 |
| D01 | 旧 V6 库迁移，包含历史命令、回执、孤儿数据及未决队列 | 旧 ID／哈希／历史不变；无自动公开、无自动重新执行 |
| D02 | 未决／UNKNOWN 时资源换项目，项目停用或删除 | 拒绝危险迁移或按冻结流程处理，不移动历史授权范围 |
| D03 | H2 与隔离 MySQL 的外键、排序规则、唯一约束和并发事务 | 两类环境都验证；不能只靠空库建表宣称迁移通过 |
| D04 | URL 编码、HEAD／OPTIONS、替代路径、错误分派和内部系统采集 | 无过滤器匹配绕过；后台系统职责不被映射成人类全局权限 |
