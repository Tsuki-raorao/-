# 09 节点采集与有界并发

## 一、为什么不能只报“心跳 QPS”

当前主要采集路径是控制中心拉取 Agent：一轮读取节点目录，分别请求 health 和 instances，校验后写 MySQL。兼容心跳接口的吞吐不能说明这条路径的节点容量。需要同时量一轮时长、完整同步成功数、实例落库数量、最旧数据年龄和远端并发数。

主流程：`AgentSnapshotSyncService.syncAll → syncNode → AgentGatewayService → AgentSnapshotParser → AgentSnapshotStore`。每个节点的 health 与 instances 仍依次请求；不同节点可以重叠执行。

## 二、优化前具体怎么实现

原 `syncAll` 遍历节点后逐个调用 `synchronized syncNode`，整个服务对象只有一把 Java 监视器锁。一台慢节点会阻塞后续所有节点，手动触发另一个节点也要等待。

每轮结束后，Spring 的 fixedDelay 才开始等待配置间隔。因此“每 60 秒拉取”准确含义是“一轮耗时 + 60 秒等待”，不是保证所有节点每 60 秒更新。

## 三、云端对照模型与结果

独立数据库 `argus_test_collection`、真实 MySQL 8.0、真实 HTTP 和实际 Spring 采集代码；Agent 由测试程序模拟，不执行 Docker。每个节点 2 个实例，health 和 instances 各固定等待 250ms，响应字段为受控测试值。协议来源标签用于验证解析器，不能将它们称为真实主机 CPU/内存数据。

测量前明确一轮预算 30 秒。此预算是本专项的容量判定目标，不等于生产默认 180 秒过期阈值。每个规模各执行一轮；下面不是统计 P95，也不是长期稳定性压测。

| 节点数 | 原顺序耗时 | 4 并发耗时 | 原最旧采样年龄 | 4 并发最旧采样年龄 | 同步成功/实例数 |
|---|---:|---:|---:|---:|---|
| 10 | 6.129s | 2.382s | 5.705s | 1.864s | 10/20 |
| 50 | 28.888s | 7.697s | 28.625s | 7.426s | 50/100 |
| 100 | 57.398s | 14.801s | 57.138s | 14.537s | 100/200 |

HTTP 请求数每轮恰为节点数×2。原并发峰值 1，新峰值 4；各轮全部节点完整同步成功，实例数量与模型一致。100 节点原实现超过 30 秒预算，改造后达到目标。

原始结果：[顺序采集](../验收证据/20261019/collection-before.json)、[有界并发](../验收证据/20261019/collection-after.json)。运行环境与读取压测相同宿主机，JVM Xmx512m、CPUQuota=100%、MemoryMax=768M；HTTP Agent 模拟器也在同一测试进程里，因此不能外推公网抖动、真实 Docker stats 耗时或上千节点容量。

## 四、代码写了什么，为什么这样写

| 代码对象 | 实现 | 设计理由 |
|---|---|---|
| `AgentGatewayProperties.syncConcurrency` | 默认 4，可配置 1–16 | 控制连接与数据库并发，拒绝无边界配置 |
| `workers` | 固定大小 ThreadPoolExecutor，队列大小等于并发度 | 不使用默认无界队列，避免一次堆积所有节点任务 |
| `ExecutorCompletionService` | 先提交最多 C 个，完成一个再提交下一个 | 按完成顺序补充窗口，慢节点不阻止利用其余槽位 |
| `inFlight` | 已提交且尚未收取结果的任务数 | 始终不超过 C，而不是为全部节点先创建 Future |
| `roundLock.tryLock` | 一轮未结束时忽略重叠整轮触发 | 避免同一目录被重复排队；fixedDelay 正常不会重入，其他触发也受保护 |
| `nodeLocks[128]` | 固定锁条带，按 nodeId hash 选锁 | 同一节点不能并发写；不会因节点删除留下无限增长的锁对象 Map |
| `syncLocked` | 保留原有单节点正常与失败逻辑 | 并发改造不放宽快照校验和失败事实 |
| `closing` / `close` | 销毁时关闭线程池，等待锁可中断 | Spring 停止后不继续启动新采集工作 |

锁条带可能让不同节点哈希碰撞而串行，代价是少量并发损失，收益是固定内存与简单生命周期。它是单控制中心进程内的保护，不宣称解决多个中央进程对同一节点的跨进程写竞争。

没有用 `parallelStream()`：公共 ForkJoinPool 与其他业务共享、并行度和阻塞 I/O 预算不直观；也没有对所有节点 `CompletableFuture.runAsync` 后一次 join，因为默认实现容易产生无界排队或共享线程池干扰。

## 五、数据库事务和数据真实性仍保持什么规则

- health 失败：OFFLINE/FAILED，保存本次检查时间和稳定错误码，不推进上次成功同步时间，不把旧指标改成 0。
- health 成功但实例失败：ONLINE/PARTIAL，只保留可确认主机观测，完整实例快照时间不推进。
- 整份清单先校验，重复 ID、负值、坏 JSON 等任一不合法不留下半份实例更新。
- `AgentSnapshotStore.save` 执行短事务，保存完整实例集合与成功时间；HTTP 请求在事务外。
- 中央实例 ID 与 Agent 局部 ID 分开；跨节点同名容器不串数据，已有实例 ID 保持稳定。
- 节点在网络等待期间已删除时，不重新创建；继续沿用已有 updateExisting/父行锁规则。

如果某节点出现未预期异常，完成队列取出该异常，记录异常类别并继续其余节点。不会将可能带连接敏感内容的异常正文直接打到日志。常规 HTTP/解析失败仍由单节点逻辑保存稳定业务码。

## 六、测试如何证明

`AgentCollectionConcurrencyTest` 验证并发上限和重叠轮次不重复采集、同节点不能重叠 HTTP 采集、单节点未预期失败不阻断其他节点。

既有 `AgentSnapshotIntegrationTest` 继续用真实本机 HTTP 与 H2 覆盖跨节点同名实例、身份稳定、读取日志、失败/部分结果、坏清单原子性、删除竞争等。两类合计 21 项回归通过；云端专项额外覆盖真实 MySQL、100 节点及并发峰值。

脚本 `CollectionBenchmark.java` 由独立主类启动同一个 Spring 应用并直接调用生产采集服务，避免新增公开管理接口；`collection-fixture.py` 只准备指定测试数据库和私有 env，定时器初始延迟设为一小时，防止后台轮次混入测量。真实游戏 Agent 与 Docker 操作没有参与本专项。

## 七、面试追问

1. 为什么不直接开 100 线程？受网络、连接池、MySQL 和每节点快照大小共同限制；当前用 4 并发先满足 100 节点受控模型，不能无限放大。
2. 为什么同节点仍要锁？不同触发若交叉完成，旧快照可能覆盖新数据；跨节点并发与节点内顺序不是一回事。
3. 采样年龄包含什么？报告在本轮结束后，以最终时间减去每个节点的 sampledAt，取最大；完整同步年龄用 lastSuccessfulSyncAt，两个指标都记录。
4. fixedDelay=60s 时最旧值大约多老？要考虑一轮耗时、等待间隔、请求延迟和失败重试，不能只答“60 秒”。
5. 还会有什么瓶颈？慢节点/超时占槽、条带冲突、数据库写入和实例规模；需按不同延迟/失败比例继续测，不由此推导百万节点或生产 SLA。
