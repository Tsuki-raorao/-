# 06 监控与告警：实现与设计取舍

## 业务目标

只看到节点列表还不够：节点很久没更新、任务失败、待发消息积压时，需要主动发现并留下恢复轨迹。当前实现站内监控与历史查询，不自动重启、不发送短信邮件。告警不能替代真实任务状态，也不能把指标未知当成恢复。

## 代码在哪里

| 类/文件 | 做了什么 | 为什么这样写 |
|---|---|---|
| `MonitoringProperties` | 绑定监控开关、阈值、新鲜度、保留天数 | 默认关闭；修改阈值无需改代码；非法值在启动绑定时拒绝 |
| `MonitoringService.tick/evaluate` | 定时评估节点、任务、Outbox 与 Broker 队列 | 仅读取已有事实，不自动执行修复 |
| `MonitoringStore.observe` | 事务内更新当前告警，仅转换时追加事件 | 重复采样不重复通知，未知值不会解除已有告警 |
| `MonitoringStore.sample/history/prune` | 写入/查询有限历史，按批清理 | 查询最多 500 点，清理最多 1000 行，避免长事务 |
| `MonitoringController` | 暴露项目授权后的查询 API | 浏览器不能通过改 projectId 查询别的项目 |
| `V11__monitoring_alerts` | 当前告警、状态事件、历史指标三张表 | 将“当前状态”“发生过什么”“指标曲线”分开存储 |
| `frontend/src/monitoring.ts` | 严格解析响应、判定评估过期、生成分段折线 | 拒绝坏响应；真实 0 保留；未知点断线 |
| `MonitoringPanel.vue` | 监控与告警页面、历史曲线、采样明细、触发恢复记录 | 让问题和证据在网页可查看，不只写进服务器日志 |

## 规则怎么判断

| 规则 | 输入 | 默认触发条件 | 恢复条件 |
|---|---|---|---|
| `NODE_OFFLINE` | HOST 节点状态、最近完整同步 | OFFLINE 或 180 秒未完整同步 | 有效节点重新在线且同步新鲜 |
| `CPU_HIGH` | 新鲜 HOST CPU、指标可用状态 | CPU ≥85% | 新鲜有效 CPU <85% |
| `MEMORY_HIGH` | 已用/总内存、指标可用状态 | 使用比例 ≥90% | 新鲜有效比例 <90% |
| `TASK_FAILURES` | 项目内 FAILED/UNKNOWN 任务更新时间 | 最近 300 秒至少 1 条 | 滑动窗口内无异常；不修改旧任务 |
| `OUTBOX_BACKLOG` | 项目内未发布事件创建时间 | 等待超过 60 秒至少 1 条 | 待发积压完成或数量降为 0 |
| `MQ_QUEUE_BACKLOG` | 主队列 ready 消息数 | ready ≥100 | 可确认 ready <100 |
| `MQ_DEAD_LETTERS` | 死信 ready 数 | 至少 1 条 | 人工处理后可确认队列为 0 |

CPU/内存先检查来源、完整同步时间、Agent 采样时间和可用状态。MOCK 数据不当成真实主机健康证据，旧值仍可供排查但不能触发“已恢复”。Broker 未启用、不可达或队列不存在时返回未知，不填成 0。

主队列与死信是共享基础设施指标，归入系统遗留项目的 platform 资源，不把全局队列统计复制给所有项目。队列当前只统计 ready 消息，不声称覆盖 unacked 和 Broker 全部内存使用。

## 为什么要把 state 和 observation_state 分开

假设 CPU 95% 触发告警，下一轮 Agent 掉线：无法证明 CPU 正常，不能自动恢复。当前保留 `state=ACTIVE`，将 `observation_state=UNKNOWN`、`observed_value=NULL`。页面同时显示“告警中”和“指标未知”。只有重新采到有效的低 CPU，才变成 RESOLVED。

如果最开始就没有指标，状态为 UNKNOWN；第一次采到正常值只建立正常状态，不产生虚假的“恢复事件”。活动 → 恢复 → 再活动会保留同一规则/资源记录，episodes 加 1，并追加新的事件。规则唯一键防止每轮产生一条相同告警。

## 表为什么分三张

- `monitor_alerts`：唯一 `(project_id,rule_key,resource_id)`，保存当前状态，适合告警列表。
- `monitor_alert_events`：保存 ACTIVE/RESOLVED 的转换，适合排查“什么时候触发、什么时候恢复”。
- `monitor_samples`：保存历史取值、可用状态、来源和监控记录时间，适合画曲线。默认保留 7 天，每轮最多清理 1000 条。

写当前状态和事件在同一事务，防止列表已恢复但事件轨迹缺失。历史点与原始 Agent 采样时间不同：此表 sampled_at 表示监控记录时间，写入前已验证 Agent 的 sampledAt 新鲜度。持续扩规模后应换专用时序存储；当前不是 Prometheus/Grafana 已接入的声明。

## 关键变量与单位

| 变量 | 单位/含义 |
|---|---|
| `now` | 本轮统一评估时间，测试可固定以验证过期边界 |
| `fresh` | 最近完整同步是否在允许窗口内，且没有明显未来时间 |
| `real` | 来源是否 HOST，避免拿 MOCK 假装真实健康 |
| `metrics` | 是否允许将本轮 CPU/内存用于判定 |
| `offline` | 1=离线/过期，0=正常，null=无法确认 |
| `memory` | `usedBytes * 100 / totalBytes`，百分比 |
| `pending` | 超过允许等待时间的未发布 Outbox 数 |
| `backlog` / `dead` | RabbitMQ 主队列/死信的 ready 数，可空 |
| `previous` | 同一规则/资源的已保存状态，事务内 FOR UPDATE 读取 |
| `transition` | 本次是否真正触发/恢复，决定是否追加事件 |
| `episodes` | 异常被重新触发的次数，不是采样次数 |
| `generation` | 前端请求代次，页面切换后丢弃旧响应 |

## API 与页面

`GET /api/monitoring/summary` 返回启用状态、当前项目告警和最近转换事件。`GET /api/monitoring/history?resourceId=...&metric=CPU_PERCENT&limit=120` 返回最近历史点；指标使用允许列表，limit 约束为 1–500。所有查询先按现有项目权限校验。

页面每 15 秒刷新。监控默认每 30 秒评估，评估结果超过 90 秒会标记未确认，防采样器停止后旧的“正常”一直显示为实时健康。曲线遇到未知点断开，不插值、不填零；可展开查看每个点的时间、值和来源。

## 发现过的真实问题

V11 开发验证先在 H2 发现 `value` 是保留字，随后 MySQL 又发现 `last_value` 与窗口函数冲突，分别改为 `metric_value` 和 `observed_value`。这些都是新迁移未发布前修正。隔离 MySQL 首次失败留下的版本记录在确认没有创建监控表后才 repair；不能照搬成生产错误时随意 repair 的操作指南。

### 2026-10-19 云端隔离验收补充

网页流程完成真实 health 503 → NODE_OFFLINE ACTIVE → 恢复采集 → RESOLVED，并断言网页显示恢复。见 [操作验收](../操作与恢复验收-20261019.md)。

专用 Broker 将消费监听器暂停，向实际主队列写入同一真实事件的 120 份副本，监控记录 ready=120、MQ_QUEUE_BACKLOG ACTIVE；恢复监听器后 ready=0、RESOLVED，收件表同一事件仍仅 1 行。再发送一条本次测试坏消息，死信 ready=1 触发 MQ_DEAD_LETTERS ACTIVE；只 ACK 移除带固定测试标识的该条死信后恢复为 0/RESOLVED，没有 purge 队列，也没有自动重放死信。

脚本：`MqFaultCheck.java`、`mq-monitor-check.py`。实际证据见 [MQ 监控结果](../验收证据/20261019/mq-monitor.json)，四次触发/恢复均有观测值与评估时间，整个过程任务数不变。首次失败暴露自定义工厂没有采用 Boot 的 listener auto-startup 设置，已在 `MessagingTopology` 显式传入并通过暂停配置回归及本次真实 Broker 复验。

这些结论证明隔离环境的告警闭环，不代表已部署到生产网站，也没有接入短信/邮件通知或外部独立探活。

## 面试追问

1. 为什么不用每次异常都发一条？持续异常会刷屏；当前按状态转换去重，重复点只更新观测。
2. 如果监控自身挂了怎么办？网页按 checked_at 判定评估过期；下一步外部探活补独立监控，不能只依赖被监控服务自证健康。
3. CPU 未采到是不是正常？不是，保持未知；已活动的告警不能因此恢复。
4. 为什么任务失败告警可以恢复但任务仍 FAILED？告警规则看近期滑动窗口，任务事实保留；两者不同。
5. 监控是否修改游戏服务？没有，采集/告警是观察链路；操作仍经用户确认和任务授权。
6. 多租户怎么避免泄漏？API 与 SQL 都约束 project_id，共享队列指标归属明确。
