# 04 远程操作与异常恢复

本章按当前源码解释实现，具体服务器复验结果另记阶段验收。读懂的目标是能回答：用户点一次重启后，系统如何避免因为网络重试而重启两次？

## 一、系统保存的事实

| 对象 | 作用 | 为什么不能合并 |
|---|---|---|
| `tasks` | 用户操作的中央记录、目标、当前状态与结果 | 用户关心的任务，不是某一次 HTTP 请求 |
| `task_queue` | 下次调度时间、领取者与租约 | 调度状态和业务状态独立；完成后调度行可移除 |
| `instance_task_locks` | 一个实例上尚未排除风险的操作 | UNKNOWN 也必须占住，不能只锁 RUNNING |
| `task_events` | 此任务每次状态转换 | 当前状态不能解释历史经过 |
| `task_event_outbox` | 与事件同事务保存的待发通知 | 网络故障不应丢掉已提交的通知意图 |
| Agent Inbox | 本机已经接收的命令、执行结果与存储身份 | 中央数据库提交不能证明远端副作用已完成 |
| 核对记录与独立回执 | 操作者如何处理不确定性 | 核对不应改写原始 UNKNOWN 历史 |

## 二、入口到结果的实现路径

1. 前端携带幂等键提交操作。中央检查身份、项目、实例、控制开关和允许目标，并核对 Agent 能力。前端按钮可用只是提示，不能代替后端校验。
2. `TaskQueueStore.enqueue` 使用 `TransactionTemplate` 开短事务，隔离级别为 READ_COMMITTED。锁住节点和实例记录，重新核对目标，再查已有幂等键。
3. 如果已有同一请求，`same` 对比实例、动作、执行模式；内容相同返回原任务，不同返回 `IDEMPOTENCY_CONFLICT`。
4. 新操作同事务写任务、持久队列、实例锁、首条事件和 Outbox。成功接收后，执行由后台 Worker 继续，接收不等于操作成功。
5. `TaskWorker.runOnce` 定时从数据库领取任务。`claim` 查到期候选，再用带条件 UPDATE 领取；影响一行才拥有执行权。
6. `process` 先核对中央目标与 Agent 的 nodeId、storeId、executionMode，再查询固定 commandId 的远端记录。
7. 查到记录就校验并使用原结果。只有同一绑定下明确返回 404、此前未确认接收且命令未过期，才允许发送原命令。发送前 `beginPost` 再确认租约所有权并保存 DISPATCHING。
8. Agent 校验命令、白名单与实例互斥，先持久化 Inbox，再进入执行。重复的相同命令返回原记录；不把每次网络请求当成新动作。
9. 中央核验回执身份和状态，`finish` 同事务保存结果、时间线、Outbox，并移除或重新安排队列。UNKNOWN 保留实例锁，等待单独核对。

中央数据库事务内不做 Agent HTTP 调用。否则远端超时期间会长时间占住行锁和连接，扩大故障影响。

## 三、关键 ID、变量和时间

| 名称 | 含义 | 重要边界 |
|---|---|---|
| `taskId` | 中央任务唯一 ID | 用于页面、审计和数据库关联 |
| `commandId` | 固定远端命令 ID | 重传不换号，否则 Agent 无法识别重复 |
| `key` / 幂等键 | 客户端同一个操作意图 | 同键不同参数必须冲突；不能每次重试都重新生成 |
| `instanceId` | 中央实例 ID | 和 Agent ID、容器名不是一个命名空间 |
| `agentInstanceId` | Agent 识别的实例 ID | 投递前核对，防止中央映射变化 |
| `targetAddress` | 接收时固定的 Agent 地址 | 不能悄悄改成后续目录中的新目标 |
| `agentNodeId` / `nodeId` | 预期 Agent 的节点身份 | 地址相同不代表仍是同一个节点 |
| `storeId` | Inbox 存储世代 ID | 重建 Inbox 后拒绝沿用旧命令恢复假设 |
| `owner` / `lease_owner` | 本次 Worker 领取令牌 | 旧 Worker 不能覆盖新领取者的状态 |
| `lease_until` | 领取权截止时间 | 到期可以恢复调度，不代表可以盲目重做动作 |
| `agentAccepted` | 曾确认 Agent 已接收 | 接收后记录消失不能再按全新命令投递 |
| `expiresAt` | 命令允许接收的期限 | 与 Worker 租约是两个概念 |
| `confirmationGrace` | 命令到期后的核实窗口 | 超出仍不能确定时进入 UNKNOWN |
| `attempts` | 投递尝试次数 | 不等于 Docker 实际执行次数 |

`TaskControlProperties` 源码默认：lease=45 秒、retryDelay=3 秒、commandTtl=5 分钟、confirmationGrace=5 分钟。实际环境可覆盖；有效租约还受 `TaskControlPolicy.safeLease` 约束，不能脱离 HTTP 超时预算独立调小。`TaskQueueStore.now` 截断到微秒，减少 Java 纳秒时间与数据库精度差异。

## 四、状态与恢复不是“失败就重试”

| 情况 | 当前处理 | 原因 |
|---|---|---|
| 请求重复且参数相同 | 返回已有任务 | 同一意图不创建第二条操作 |
| 同实例仍有未解决任务 | 拒绝新操作 | 防止启停与重启互相覆盖 |
| Worker 崩溃 | 租约到期后重新领取，先查远端记录 | 调度可恢复，副作用不可盲目重放 |
| POST 超时/响应丢失 | 进入核实和重试查询流程 | 无响应不能证明 Agent 没执行 |
| 远端曾接收，后续返回 404 | UNKNOWN / AGENT_RECORD_LOST | 可能丢失去重存储，不能再次执行 |
| 节点、地址、存储或执行模式变了 | UNKNOWN | 不能把旧任务发给新的目标 |
| 命令过期且同绑定明确缺失 | FAILED / COMMAND_EXPIRED_ABSENT | 已不能接收且有明确缺失证据 |
| 核实窗口结束仍无结论 | UNKNOWN / CONFIRMATION_EXPIRED | 保留事实不确定性和互斥 |
| 旧 Worker 迟到回写 | 所有权/租约检查不通过，不更新 | 领取权不是永久有效 |

“先查再发”自身不是 Exactly Once 保证；固定 commandId、Agent 持久去重、目标绑定和不确定时停止自动执行共同约束风险。MySQL、HTTP 和 Docker 不存在一个共同原子事务。

## 五、Agent 为什么需要持久 Inbox

入口 `agent/.../service/TaskService.java`，存储 `TaskInbox.java`。

- `TaskInbox` 独占存储目录的文件锁，避免两个 Agent 进程同时使用同一套去重记录。
- `store.id` 持久保存存储身份。已有任务文件却缺失身份时拒绝启动，不能创建新身份后假装旧证据仍然有效。
- 任务记录有格式与身份校验，使用文件 force 和原子替换；持久写成功后才更新内存视图。存储异常使 Inbox 不健康，拒绝后续新执行。
- `TaskService` 启动恢复时将遗留 RUNNING 变为 UNKNOWN。进程退出时无法仅凭记录判断 Docker 是否已完成，直接再次执行可能重复重启。
- `unresolved` 保存实例与未解决命令的关联；UNKNOWN 仍在其中。核对完成才按具体命令解除，避免解除别人的锁。
- 这是有容量边界的单机持久存储，不是多副本数据库。磁盘永久损坏和机器整体丢失仍需运维备份及人工判断。

## 六、人工核对为什么单独设计

入口 `TaskReviewController` / `TaskReviewService`，Agent 端 `TaskService.reviewEvidence/resolve`。

核对先读取原命令、持久记录与当前容器观测。操作者提交理由和证据后，系统保存独立核对记录，并向同一 Agent 申请绑定原命令的回执。Agent 核对原任务、容器映射、锁归属和执行进程状态，持久保存回执后再解除本机对应互斥；中央应用回执时也必须核验对应关系。

原 UNKNOWN 保留，因为“人工允许继续操作”不等于“历史命令肯定成功/失败”。核对本身不执行 start/stop/restart；后续操作是新任务、新意图。不能用历史回执清除新任务占用的锁。

## 七、Redis 在这条路径的实际位置

`AfterCommitNotification` 在事务提交后调用 `RedisTaskStateCache.put`，key 默认 `argus:task:<taskId>`，JSON 值，TTL 默认 120 秒。Redis 异常被捕获，任务事实仍保存在 MySQL。

当前接口没有从 Redis 读取任务，因此准确说法是“可丢失的任务热状态副本”。它没有承担持久队列、实例互斥或消费去重。提交后回调仍可能花费网络等待时间，故障不回滚业务不等于响应完全不受延迟影响；性能阶段应测连接超时和故障耗时。

## 八、面试追问及证据要求

1. 为什么不直接同步调用 Docker？请求生命周期无法覆盖跨进程恢复与结果核实，持久任务把接收、调度和结果分开。
2. 为什么同时有幂等键和实例锁？前者识别同一个意图，后者禁止不同意图对同一实例并行冲突。
3. 为什么 UNKNOWN 不算 FAILED？FAILED 表示有失败结论，UNKNOWN 表示无法证明副作用是否发生，不能采取相同重试策略。
4. 为什么数据库锁还不够？本地提交无法阻止远端在 HTTP 超时后继续执行；还需要命令去重、身份绑定和执行进程检查。
5. 如何证明没有重复执行？关联 taskId、commandId、Inbox 和容器实际状态/启动时间；仅统计 HTTP 200 次数不够。
6. 哪些还需要复验？当前轮次浏览器启停重启、丢回执、人工核对、重复提交及物理容器核验必须逐项记录到阶段②，不能因为本章已写就勾选通过。

## 九、数据库进程重启的实际验收

`mysql-restart-check.py` 仅对隔离 MySQL 操作：先暂停中央 TaskWorker 的启动并关闭验收 MQ，让真实 HTTP 接收一条 START，但尚未投递到 Agent。此时 task=PENDING、task_queue=1、Outbox=PENDING 1，Agent Inbox 没有该命令。

实际重启 MySQL 容器约 5349.749ms 后，上述三个数据库事实保持。恢复原 Worker/MQ 配置后，原 taskId/commandId 最终 SUCCEEDED，5 条状态事件对应 5 条 PUBLISHED Outbox 和 5 条消费收件，原 commandId 只对应一个 Inbox；最后用新 STOP 任务恢复测试容器停止状态。

这验证了“中央调度与待发意图依赖持久数据库而非 JVM 内存”，不是只重启应用或捕获数据库异常。该脚本没有重启生产数据库，没有将未确定的远程动作直接重放，也没有删除历史任务。

证据：[数据库进程重启恢复](../验收证据/20261019/mysql-restart.json)。配合阶段②在途中央重启和浏览器丢回应验证，分别覆盖不同故障点，不能用其中一个替代全部场景。
