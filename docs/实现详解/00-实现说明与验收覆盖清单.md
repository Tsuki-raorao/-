# 00 实现说明与验收覆盖清单

本文规定交接资料需要解释到什么程度。它也是防止遗漏的检查表，不代表下面所有能力均已完成或上线。

## 每项功能必须回答的问题

1. **做什么**：谁在什么场景发起，解决哪个具体问题，成功后留下什么事实。
2. **写了什么**：对应目录、类、方法、接口、表、配置和测试；从入口能一路找到实现。
3. **怎么写**：输入校验、正常时序、状态变化、读写 SQL、返回结果，关键变量的名称、含义、单位与作用域。
4. **为什么**：选择此实现的理由、替代方案、成本与适用规模，不能只写“提升性能”“保证可靠”。
5. **失败怎么办**：超时、崩溃、重试、重复、乱序、并发竞争、依赖不可用、旧数据兼容。
6. **边界在哪里**：事务起止、锁对象、权限检查、项目隔离、网络调用、事实来源和可丢失副本。
7. **如何证明**：测试名称、实际环境、复现步骤、结果与限制；源码实现、隔离测试、生产启用分别记录。
8. **面试怎么讲**：正常流程一遍、故障流程一遍、设计取舍和仍存在的问题各一遍。

## 当前需要明确保留的限制

- RabbitMQ 消费者目前核对并持久保存任务事件收件记录；不能说已经实现短信、邮件或用 MQ 驱动 Docker。
- Redis 当前实现是提交后的任务状态副本写入；查询链路仍以 MySQL 为准，不能填写“缓存命中率”或“查询耗时降低”的成绩。
- 存在索引不等于做过慢 SQL 优化。只有查询、数据集、执行计划和同环境前后耗时齐全，才记录优化结论。
- 隔离环境的真实云服务器测试，不等于生产业务已启用。每阶段必须分开注明。
- 全量用户注册与管理仍按用户要求后置；AI 由另一会话开发，不能把已有目录当作整体功能完成的证据。

## 阶段资料的验收方式

每阶段交付“改动清单 → 设计解释 → 字段/变量字典 → 正常与异常时序 → 原始测试证据 → 未完成项”。未完成的专项明确标记，不用完成率代替证据。
