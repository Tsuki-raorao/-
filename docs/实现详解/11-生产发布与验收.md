## 二、为什么分成 start / gray / finish

`deploy/messaging/release-stage.py` 维护一个发布状态，而不是把多个有副作用的步骤放进无条件重跑的 shell。

| 阶段/变量 | 做什么 | 为什么 |
|---|---|---|
| `PREPARED` | 校验备份与候选哈希、检查没有在途任务，写不可变版本目录 | 先证明可恢复，拒绝覆盖已有发布 |
| `MQ_STARTED_MONITOR_PAUSED` | 新 jar 启动，MQ 开启，暂缓告警 | 让临时灰度资源不产生业务告警与历史点 |
| `grayIds` | 本次临时项目、节点、实例、任务、事件、Outbox 的独立 UUID | 精确核对和清理，不能删除其他数据 |
| `MQ_GRAY_PASSED` | 数据库提交→发布 confirm→消费收件通过，临时事实清理完成 | 端口能连、Broker ACK 都不足以证明业务消费 |
| `PUBLISHED` | 开启监控、核对 API 和写保护，最后发布静态入口 | 页面出现新能力时后端应已可用 |
| `originalEnvironmentHashes` | 原三份运行环境文件的内容摘要 | 证明既有 Redis/AI 等配置未被改写 |
| `artifactSha256` | 实际运行 jar 的摘要 | 防止验证了一个包却启动另一个包 |

临时 mysql client 文件在受保护目录内创建，密码不进命令行，退出后删除。公开结果只含状态、计数、哈希和节点不透明 ID，不输出地址、令牌或业务日志正文。

## 三、数据库备份与回退依据

发布前保存应用库逻辑备份、旧 jar、旧静态站点、systemd 定义和原环境文件，8 个持久备份项逐一验证 SHA-256，gzip 完整性通过。生产 V9 备份在独立库恢复并迁移到 V12，19 张既有业务表按主键排序、逐字段计算内容指纹，迁移前后全部相同。

然后用真正备份下来的旧 V9 jar 启动到隔离 V12 库：健康检查、节点/实例/任务/日志读取通过，只读状态保持。由此获得本次“新增表/索引后旧应用仍能读取”的兼容依据；没有在生产反复切版本来冒充隔离演练。

`start` 启动或关键不变量失败时移除本次专用 override、恢复此前消息配置并启动旧 unit。不会自动用旧数据库备份覆盖新库，因为那可能丢掉备份后的新增事实。实际生产没有执行数据库回退。

证据：[备份校验](../验收证据/20261019/production-backup-verified.json)、[副本迁移](../验收证据/20261019/production-copy-migration.json)、[旧应用兼容](../验收证据/20261019/old-release-compat.json)。

## 四、生产 MQ 灰度如何避免误操作游戏

灰度先在单独 ARCHIVED 项目中写带明确说明的 MOCK 测试事实，同事务保存 tasks、task_events、Outbox。没有 commandId、没有 task_queue，不向 Agent 投递。实际生产 Worker 将 Outbox 标为 PUBLISHED，实际消费者核对事实并写入一条正确收件。

确认成功后按外键顺序清理本次唯一 UUID 对应的事实和资源，再核对全部归零。最终审计再检查一次，不留下伪造的游戏成功记录。它是**生产受控合成验证**，不是一次真实用户操作。

另向生产事件交换机投递一条固定测试标识的坏消息，实际消费者拒绝后进入死信；监控在 ready=1 时触发、移除这条测试消息后恢复到 0。仅 ACK 清理本次测试消息；遇到其他消息会保留并停止，未 purge、未自动重放。

证据：[最终发布审计中的 gray](../验收证据/20261019/production-final-audit.json)、[生产死信触发与恢复](../验收证据/20261019/production-mq-monitor.json)。最终主队列 ready=0、死信=0，消费者连接正常。

## 五、发布后发现并修复的内存口径问题

旧 Agent 从 JDK 获取 free memory，再计算 total−free。在两台 Linux 主机上，该口径将缓存占用也算进“使用率”；控制机显示约 94%，但内核仍有约 1.5GB available。

Linux 现在读取 `/proc/meminfo` 的 `MemTotal`、`MemAvailable`，使用 `total−available`。`MemAvailable` 是内核对无需交换即可供新应用使用内存的估算，考虑部分可回收缓存；参见 [Linux 内核说明](https://www.kernel.org/doc/html/latest/filesystems/proc.html)。它仍是估算，不是进程 RSS 总和，也不能单独代表所有内存压力。

实现入口 `agent/.../HostMetrics.fromLinuxValues`：严格解析 kB→byte、拒绝溢出/负数/重复字段；若 JDK 总量与 `/proc` 总量不一致，不把容器限额和宿主机 available 混算；异常时保留可确认 CPU/总量，已用内存保持未知。非 Linux 保留 JDK 路径。

92 个 Agent Java 场景及 3 组独立 JSON 契约检查通过。两台 Agent 升级前确认没有 PENDING/RUNNING 命令，升级后配置、节点/存储身份、能力与 Inbox 文件摘要均不变。控制机测得约 57%，工作负载机约 51%；这些是修正后的占用估算，**不表示释放了相应数量的内存**。

旧历史点和告警事件没有回写。内存告警按新有效采样恢复，跨版本比较需要结合本次采集口径变更时间。证据：[控制机](../验收证据/20261019/agent-memory-control.json)、[工作负载机](../验收证据/20261019/agent-memory-workload.json)。

## 七、验收工具本身的修正

- 只读生产没有启用操作令牌，读取凭据提交写请求先得到 403/OPERATOR_REQUIRED；工具原来只预期 405，已按实际身份核对拒绝原因。没有为测试额外开放写权限。
- loopback:80 的默认虚拟主机属于同机其他站点；审计补上 Argus Host 头后验证正确入口，公网 IP:80 也通过。Nginx 路由未为测试而修改，协作中转站未改动。
- 内部 Agent 读取 API 按真实控制器 `/api/agent-gateway/nodes/{id}/health` 验证，不把测试脚本猜错 URL 的 404 当成服务故障。

## 八、本轮不作出的声明

生产继续全局只读，真实启停/重启与人工核对在独立 Docker 环境验收；没有对游戏服做这些发布验证动作。MQ 当前消费结果是持久收件记录，没有短信/邮件/自动死信重放；Redis 当前是副本写入，没有读缓存命中率成绩。单 Broker/单控制中心不等于集群高可用。AI 与完整用户体系仍按后续阶段推进，本轮保留既有 AI 配置和二进制类，不将其算作 AI 集成验收。

## 九、验收环境收尾与复现

生产验收后，独立环境的 5 个测试数据库以及验收目录（含 35 条任务、35 份 Inbox 和配置）已归档在工作负载机 `/opt/argus/backups/acceptance-archive-*` 私有目录；文件摘要和 gzip 解压一致性已核对。压测/验收的 4 个进程及 3 个专用测试数据库/消息/Redis 容器停止，原数据与卷保留，没有删除数据库或容器。正式 Agent 和正式 Broker 保持运行，游戏容器基线仍不变。证据：[隔离环境归档](../验收证据/20261019/acceptance-archive.json)。

重做验收先明确使用独立端口/数据库，检查私有目录与备份摘要，启动原专用 MySQL 和 RabbitMQ，按需启动测试 Redis；核对配置后用 `server-fixture.py start` 启动 Agent、中央、故障代理。性能进程需要独立按性能章节启动，不是该 start 命令的一部分。已有数据不可重新执行 prepare/seed；需要全新测试数据应另建隔离库，并保留旧证据。若测试新修正的内存口径，应先重建验收 Agent 包，不能把保留的旧测试包当作本轮最终生产 Agent。

本轮归档是可复查保留，不等于完成阶段⑦全项目灾难恢复演练。
