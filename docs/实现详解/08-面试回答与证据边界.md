# 08 面试回答与证据边界

本章帮助把“写过代码”变成能解释取舍、有证据的回答。不要把仍在进行的阶段描述为全部上线；完整用户体系与 AI 验收不属于本轮完成声明。

## 一、介绍项目怎么说

未序 Argus 是面向多节点服务的运维控制平台，中央 Spring Boot 管理节点与实例、持久操作任务和审计轨迹，服务器 Agent 负责采集与白名单内的 Docker 操作。MySQL 保存权威任务事实，通过幂等键、实例互斥、Worker 租约和 Agent 持久 Inbox 处理重复请求与不确定结果；任务状态通知使用 Outbox 和 RabbitMQ，Redis 保存可丢失的热状态副本。当前已在云端隔离环境验证网页操作与恢复、队列消费及告警，并完成真实 MySQL 数据集上的读取压测与索引前后对照。生产灰度与更大规模采集验证仍需按阶段完成。

## 二、常见追问如何对着代码回答

| 问题 | 回答主线 | 代码/证据入口 |
|---|---|---|
| 为什么不点按钮就直接调 Docker？ | 同步请求不能可靠覆盖接收、跨进程恢复与结果核实；中央先保存任务，再由 Worker 调度 | `TaskQueueStore`、`TaskWorker`；04 |
| 幂等怎么实现？ | 请求幂等键识别同一意图；参数冲突拒绝；Agent 固定 commandId 去重；实例锁处理不同意图冲突 | `same/enqueue`、Agent `submit`；网页双击/丢 202 专项 |
| 重启动作到底会不会重复？ | 不能宣称跨 MySQL/HTTP/Docker Exactly Once；回执丢失先查原记录，存储身份变化或无法证明时 UNKNOWN 并保留互斥 | 04；浏览器故障与在途中央重启证据 |
| 中央服务重启后任务怎么办？ | 队列在 MySQL，租约决定谁接管；先查询原命令，不生成新命令编号 | `claim/process`；restart-control.json |
| UNKNOWN 为什么不直接改失败？ | 不确定副作用是否发生，失败重试可能再次重启；独立核对保留原历史 | `TaskReviewService`；04 |
| 锁是 Redis 实现的吗？ | 不是。当前实例互斥在 MySQL，以唯一约束和事务维护；Agent 还有本地未决命令与执行进程约束 | `instance_task_locks`、`TaskInbox` |
| MQ 用在哪个业务？ | 承载任务状态事件通知，当前消费者核实并保存收件事实；不是 Docker 命令通道，也未实现短信/邮件 | `MessagingTopology`、`TaskEventConsumer`；03 |
| 数据库提交成功，消息没发怎么办？ | 业务状态/事件/Outbox 同一事务提交，后台领取发送；失败退避，过期 PROCESSING 可重新领取 | `TaskEventOutboxRepository/Worker` |
| confirm ACK 和消费 ACK 区别？ | 前者确认 Broker 接收，后者确认消费者处理；数据库提交后 ACK 丢失仍可能重投，因此消费唯一键兜底 | `RabbitTaskEventPublisher`、`@Transactional consume` |
| 死信怎么处理？ | 有界消费重试后拒绝且不重回主队列，DLX 路由到死信；监控触发后人工排查，未实现通用自动重放平台 | 03、06；mq-monitor.json |
| Redis 为什么存在？ | 已有实现保存任务热状态副本，TTL 到期可丢；持久任务、锁与去重仍由 MySQL/Inbox 负责 | `RedisTaskStateCache`；不能虚构读取命中率 |
| 事务如何划分？ | 数据库短事务包任务、事件和锁等一致事实；HTTP 在事务外；Redis 提交后写；消费收件同事务去重 | `TransactionTemplate`、`AfterCommitNotification` |
| 为什么数据库分这么多表？ | 当前事实、调度、互斥、追加事件、人工核对、待发通知是不同生命周期；分表便于约束和恢复 | 02 的 24 表/239 字段实录 |
| 高并发测了多少？ | 已测 20 闭环并发、5 分钟、10 万任务/10 万日志，5 类真实只读接口；不能说测出了系统峰值 | 05 与 read-after.json |
| 具体压测结果？ | 索引优化后 138840 次，462.743 次/s，P95 88.367ms，P99 141.177ms，0 错误；明确是隔离云环境 | 05；原始 CSV 归档 |
| 优化前失败了吗？ | 是，基线 4.776 次/s、P95 约 10s、错误率 9.4456%，主要任务查询超时；失败数据未删除 | read-before.json |
| 慢 SQL 怎么找？ | 本轮先从业务压测发现退化，沿 Repository 定位查询，EXPLAIN ANALYZE 核对扫描/排序；没有把它说成生产慢日志告警 | 05、sql-before/after.json |
| 为什么已有索引还慢？ | 项目单列索引仍命中十万行；任务排序 ASC/DESC 混合与原全升序索引方向不同 | V12、05 |
| 联合索引列顺序为什么这样？ | project 等值前缀，日志时间顺序；失败统计 status 范围再 updated_at；任务显式 created_at DESC,id ASC | `V12__query_indexes` |
| 怎么证明是索引起作用？ | 同批数据与同类负载前后对照，加上实际计划从扫描十万行变为 100/20 行；也说明缓存和共用宿主机限制 | 05 |
| 监控怎么避免告警刷屏？ | 当前规则/资源唯一，只有状态转换追加事件；未知值不自动解除活动告警，重新异常增加 episodes | `MonitoringStore.observe`；06 |
| 节点没数据就显示 0 吗？ | 不显示。保存来源、采样与同步时间；过期和未知独立标记，历史曲线未知处断开 | `MonitoringService`、`monitoring.ts` |
| 不同项目怎么隔离？ | 后端先授权，SQL 按 project_id 过滤；全局 MQ 指标不复制给每个项目；完整身份产品化仍后置 | `MonitoringController`、02、07 |
| 如何扩容？ | 先区分读取、采集、控制、通知瓶颈；当前读取已有证据，顺序采集是待测限制，不能由读 QPS 推算节点规模 | 阶段③剩余项 |

## 三、建议现场画的两条链路

操作：浏览器确认 → MySQL 任务/队列/锁/事件/Outbox 提交 → Worker 领租约 → 查 Agent 原 commandId → 必要时投递 → Inbox 持久去重 → Docker → 核验回执 → 中央终态或 UNKNOWN。

通知：业务事务写 Outbox → Worker 领取代次 → 持久消息/confirm/return → 标记发布 → RabbitListener → MySQL 核对与唯一收件 → 提交后 ACK；失败有界重试后死信。

两条链路职责不同，不要把“消息已发布”当成“容器执行成功”。

## 四、被问到未完成能力时

“这一项尚未在当前环境验收。我现在的实现是……，已经验证的是……，下一步准备通过……证明。”随后指出阶段安排。不要编造百万 QPS、Redis 缓存命中率、跨机容灾、AI 准确率或未实施的自动修复能力。
