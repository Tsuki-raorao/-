# 常驻消息服务与生产灰度准备

2026-10-19 最终状态：生产已升级 V12，MQ/监控启用，保持只读及远程操作关闭。实际 Outbox→Broker→收件、死信告警触发/恢复和最终只读审计均已通过。部署脚本与完整过程见 [生产发布与验收](../../docs/实现详解/11-生产发布与验收.md)。以下准备过程按时间保留，其中未切换说明属于发布前状态。

本文解释本轮部署准备及剩余切换步骤。实际主机、密钥、密码只保存在私有运行配置中；文档用逻辑角色描述，不包含真实地址。

## 角色和链路

控制主机：Spring Boot、Nginx、现有 Redis。工作负载主机：游戏服务、独立 RabbitMQ。数据库主机：已有 MySQL。新 MQ 不要求把 Redis 或 MySQL 装到用户电脑。

链路为控制中心 → 控制主机 loopback:25674 → systemd 管理的 SSH 通道 → 工作负载主机 loopback:25674 → 容器 AMQP:5672。跨主机流量经过 SSH 加密；没有公开 AMQP 或管理页面端口。

## 实际创建了什么

| 对象 | 作用 | 为什么这样设置 |
|---|---|---|
| `argus-rabbitmq-prod` 容器 | 常驻独立 Broker | 与之前验收 Broker 分开，不共享队列、账号和数据 |
| 同名 Docker volume | 保存 RabbitMQ 数据 | 重建容器不应丢掉持久队列 |
| 固定 hostname `argus-mq` | 稳定 Rabbit 节点身份 | 数据目录与节点名相关，不能每次随容器随机 hostname 改变 |
| `unless-stopped` | Docker 重启后自动恢复 | 避免临时 shell 进程退出就停止服务 |
| 384MiB/0.5 CPU 限额 | 限制 Broker 对宿主机影响 | 原型负载很小，不抢占游戏服务无限资源 |
| `argus-mq-tunnel.service` | 固定目标 SSH 转发、断线重连 | 不依赖本地电脑持续在线 |
| 独立 ed25519 key | 仅用于 MQ 通道 | 在控制主机上生成，原云访问私钥没有复制到服务器 |
| 已信任 known_hosts | 固定目标主机公钥 | StrictHostKeyChecking=yes，未以关闭校验来绕过连接问题 |
| 专用 authorized_keys 行 | 禁止 shell、限制本地转发目的地 | 不修改其他已有 SSH 访问凭据 |
| `client.env` | 待切入的 MQ/监控环境变量 | 只有应用 unit 引用后才生效，文件存在不代表已经启用 |

私有目录 `/etc/argus/messaging` 权限 0700，配置/密钥 0600。`prepare-broker.py` 的 `export-client-private` 明确只用于重定向到私有文件，禁止把输出粘贴到日志或仓库。

## 发布前准备记录

已验证：控制主机使用专用账号通过私有通道发布持久消息并收到 confirm；工作负载主机实际重启 Broker 后，从控制主机读回同一消息，确认持久投递属性，ACK 后删除专用 smoke 队列。没有修改业务队列。证据：[生产准备结果](../../docs/验收证据/20261019/production-mq-readiness.json)。

生产应用进程检查仍为 MQ=false、monitoring=false、read-only=true、task-control=false、task-review=false，原有 Redis 和 AI 配置保持。**这不是生产业务 Outbox/消费全链路已经验收的声明。**

## 发布前备份和演练

`backup-before-release.py` 从运行中服务的环境读取数据库配置，临时生成 0600 的 mysql client 配置文件，完成后删除；密码不进入命令行。使用 mysqldump 单事务备份应用库，另保存当前 jar、静态站点、systemd 定义和三份既有环境文件，私有目录写 manifest 哈希。临时凭据文件不作为可恢复备份项。

`verify-backup.py` 已逐文件复核 8 个持久备份项及 gzip 完整性。初始 manifest 曾误列随后删除的临时 client 文件，已修正生成器和该项元数据，没有修改备份 SQL 内容。见 [备份验证摘要](../../docs/验收证据/20261019/production-backup-verified.json)。

发布前生产库为 V9。备份已在独立 `argus_test_release` 恢复；`MigrationSmoke.java` 按主键顺序对每张原有业务表逐列生成长度分隔 SHA-256 指纹，再执行 V10/V11/V12，复核 19 张既有业务表行数和内容指纹完全相同。新表和索引通过真实 MySQL 验证，不是只运行 H2。证据：[生产副本迁移](../../docs/验收证据/20261019/production-copy-migration.json)。该演练时生产库尚未执行迁移；后续发布已经完成 V12。

## 本次采用的灰度执行顺序

1. 核对备份文件哈希、剩余磁盘空间、当前无在途操作，记录已测试候选 jar 的哈希及源码提交。
2. 在不可变 release 目录安装候选 jar；保留现有三份环境文件与 AI 参数，只追加消息配置，保持全局只读与真实控制关闭。
3. 启动新版本并核对 MySQL 迁移、健康检查、MQ 发布/消费及受控测试事实。不要把无路由 ACK、坏消息拒绝或仅端口连通当成成功消费。
4. 在受控测试期间避免测试资源混进真实告警；结束后清理明确标识的测试事实并核对原资源，启用监控和对应静态页面。
5. 验证 IP 入口、节点/实例/任务/日志/监控、鉴权与写保护、真实指标新鲜度和队列计数；记录恢复路径。完成后才勾选阶段①与④生产灰度。

回滚优先恢复旧 jar/环境与静态站点；数据库迁移目前为新增表/索引，但不能仅据此假定旧版本可运行，切换前还应验证旧版本与升级后 schema 的兼容。若需数据库还原，应停写并评估备份后新增事实，不能直接覆盖并丢掉新数据。

## 当前运维边界

这是单 Broker、单宿主机持久存储，不是 quorum 集群或跨节点容灾。常驻和重启恢复不等于高可用。卷备份、磁盘/队列资源容量和客户端重连仍需监控；管理端口未开放，不用公网管理页面换取方便。
